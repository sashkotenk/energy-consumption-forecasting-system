# ADR-024: Artifact-backed bounded exports

- Status: Accepted
- Date: 2026-08-07

## Context

Forecast results contain exactly 24 points and persisted experiment comparison data is bounded by the
fixed algorithm, fold and horizon protocol. TASK-16 requires forecast CSV, experiment metrics in
CSV/JSON, the persisted experiment manifest and chart-ready data, while keeping filesystem paths
private and preserving checksums. The system already owns an Artifact Service, `app.artifacts`
metadata and an external-access-control deployment assumption from ADR-009.

The earlier design draft mentioned a direct forecast export response and PNG chart output. The
implementation task instead requires generated export artifacts and chart-ready data. Returning files
directly from domain endpoints would bypass artifact provenance and would make path/purpose controls
harder to centralize.

## Decision

1. Export creation is synchronous because every supported TASK-16 payload is bounded: one 24-point
   forecast or one persisted experiment result set. Export work must move to the existing `export`
   job type only if future formats become unbounded or computationally expensive.
2. Generated bytes are published through the existing `ArtifactService`. PostgreSQL persists purpose,
   media type, original download name, size and SHA-256; the local store keeps opaque generated keys.
3. Forecast CSV uses `forecast_export`, chart-ready JSON uses `chart`, metrics CSV/JSON use `metrics`,
   and the experiment result manifest uses `manifest`. No new artifact kind or database column is
   introduced.
4. A dedicated application download endpoint accepts only artifact IDs whose purpose is in the
   export allowlist. Raw datasets and model bundles are never downloadable through this endpoint.
5. API responses expose export metadata and checksum, but never `storage_key` or an absolute path.
   The download filename is sanitized before building `Content-Disposition`.
6. Missing/deleted metadata returns RFC 9457 Problem Details with HTTP 404. Export metadata whose
   stored bytes are unavailable returns HTTP 410. A non-export purpose returns HTTP 403. A failed
   experiment cannot create a successful export and returns HTTP 409.
7. CSV is encoded as UTF-8 with an explicit, fixed column sequence. Text cells that begin with a
   spreadsheet formula prefix (including after leading whitespace) are prefixed with an apostrophe.
   Numeric values remain numeric.
8. Chart export is presentation-independent JSON containing timestamps, horizons and actual/predicted
   energy series. PNG rendering stays a frontend concern unless a later requirement explicitly adds a
   trusted server-side renderer.

## Consequences

- Export provenance, cleanup behavior and checksums reuse a single existing storage abstraction.
- No Alembic migration or schema-design DDL change is required for TASK-16.
- Download authorization is purpose-based only because the baseline has no built-in user identity.
  Deployments exposed beyond localhost/private networks still require external access control.
- Repeated export requests create immutable artifact rows instead of mutating previous files. This is
  simple and reproducible but can accumulate redundant bytes; retention/deduplication is a later
  operational concern.
- The generated TypeScript client remains TASK-17 scope; TASK-16 updates the runtime and design
  OpenAPI shape but does not start frontend SDK synchronization.
